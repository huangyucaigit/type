# 部署与恢复

本文维护本项目的发布步骤、恢复边界及共享网站入口约束。用户功能说明见 [使用帮助](../about.html)，本地启动和功能测试见 [README](../README.md)。修改部署流程、服务依赖或数据目录时，同步更新本文与部署测试。

## 服务与管理边界

正式网站为 `https://type.where.work/`，服务器为 `47.106.182.159`，部署目录为 `/opt/zijian`。容器编排工具（Docker Compose，按配置启动和连接网站服务）管理本项目的 `app` 和 `web`：`app` 使用 `node:24-bookworm-slim`，监听容器内部的 4173 端口；`web` 使用 `nginx:stable-alpine`，接收外部 80、443 端口请求。源码目录只读挂载，更新源码无需重新构建应用镜像。

Nginx 是多个域名共用的网站入口。`pay.where.work` 的支付服务在另一个仓库，本项目保留既有转发并检查可达性。练习网站负责自己的订单、支付通知接收和时长发放，支付服务负责商户侧付款。本机预览使用模拟模式，正式站点已部署并启用真实微信 Native 支付，2026-10-17 已通过真实 1 分付款、通知 ACK、增加 1 天与重复通知不重复发放的验收；公网不开放模拟成功入口。模式、配置及验收记录见 [支付接入](PAYMENTS.md)。

| 本仓库维护的路由 | 对应外部依赖 |
| --- | --- |
| `type.where.work/payments`、`/payments/` | 跳转至 `https://pay.where.work/demo/` |
| `type.where.work/payments/notify` | 转发到本项目 `app`，接收支付服务的签名业务通知；必须优先于 `/payments/` 演示跳转 |
| `type.where.work/business/type-demo-live`、`/business/type-demo-sandbox` | 转发至 `wechat-pay-demo:18088` |
| `pay.where.work` 的 `/health`、`/api/v1/`、微信支付回调 | `wechat-pay-service:18087` |
| `pay.where.work` 的演示、管理及演示回调入口 | `wechat-pay-demo:18088` |
| `pay.where.work` 的证书验证、文档及客户端包下载 | `pay-acme:80` |

上述容器由支付项目维护，需能在 `web` 所在网络中按这些名称解析。支付项目负责其部署、凭据、数据、支付域名证书及续期。本项目的发布和回退不能删除支付路由，也不部署、停止、恢复支付服务或支付数据；无需访问支付管理页面或创建真实订单来验证路由。

## 文件与数据范围

| 服务器路径 | 用途与恢复规则 |
| --- | --- |
| `src/` | 页面、样式及程序源码；发布替换变化文件，代码回退恢复对应版本 |
| `compose.yaml`、`nginx.conf` | 本项目容器配置与共享入口配置；后者变更需显式确认参数 |
| `config/app.env` | 本项目 DeepSeek、邮件、保留的阿里云短信及支付配置；私有文件，随版本快照备份与回退 |
| `tls/type.where.work.pem`、`tls/type.where.work.key` | 本网站证书与私钥；随版本快照备份与回退 |
| `data/` | 留言及防重复提交数据，以及 `auth.sqlite` 中的账号、会话、游客体验、券、邀请奖励、订单、支付通知与权益发放记录；每次发布和手动回退前独立备份，代码恢复不覆盖现存数据 |
| `tls/pay.where.work.*` | 外部支付项目的证书；本项目不上传、备份或回退 |
| `.backups/`、`.data-backups/`、`.releases/` | 私有代码快照、独立业务数据快照及发布记录；不能放入源码静态目录、提交仓库或公开下载 |

浏览器中的最近范文保存在用户自己的本地存储中，不在服务器 `data/` 里，服务器备份无法恢复这些范文。支付项目的数据目录也不属于本项目的备份范围。

## 发布前准备

本机需要 PowerShell、Node.js 22.22 或更新版本（生产镜像使用 Node.js 24），以及 `ssh`、`scp`、`tar`；远端需要 Python 3.6 或更新版本、Docker Compose 和 `curl`。本地部署测试需要 Python 3.6 或更新版本。默认通过 SSH（加密远程连接）使用 `$env:USERPROFILE\.ssh\codex_linux` 登录服务器，保留已校验的主机记录。

1. 确认本次代码范围及 Git 提交，检查用户功能说明是否仍与实现一致。部署脚本发布工作区文件，不能只凭提交号判断工作区内容。
2. 在项目根目录运行下列测试。部署测试使用临时目录和模拟命令，不连接服务器、不启动容器、不调用模型或支付服务。

   ```powershell
   node --test tests/*.test.cjs
   python -m unittest discover -s tests -p test_deploy_release.py -v
   ```

3. 保证本机 `tls/type.where.work.pem` 和 `tls/type.where.work.key` 有效。脚本检查证书域名、有效期、证书链签名及私钥匹配；本机 `tls/`、`.env` 已排除版本管理。
4. 初次部署需提供 `.env` 中的 DeepSeek、邮件及保留的阿里云短信配置，并先由支付项目准备外部服务网络与支付域名证书。账号或支付配置新增、轮换时，需使用 `-UpdateSecrets` 同步私有环境文件；普通发布默认保留远端现有环境文件。支付默认不开放真实付款；启用真实模式之前核对 [支付配置与验收](PAYMENTS.md)。首次部署没有可恢复的旧网站版本；不能将首次部署失败描述为回退成功。
5. 发布前确认有足够磁盘空间保存代码与业务数据快照。任一备份失败会阻止覆盖在线文件。

## 常用命令

普通发布：

```powershell
.\deploy\Deploy.ps1
```

后续发布默认保留服务器密钥及环境配置。首次同步新增账号、消息发送或支付配置，或明确需要轮换这些配置时，使用：

```powershell
.\deploy\Deploy.ps1 -UpdateSecrets
```

本地与远端 `nginx.conf` 存在实际内容差异时，默认停止发布，避免用过期入口配置覆盖支付仓库的更新。先对照远端配置合并差异，确认保留支付路由，再显式执行：

```powershell
.\deploy\Deploy.ps1 -UpdateProxyRoutes
```

该参数表示允许应用已经核对过的共享入口变更，不会自动合并两个仓库的配置。单纯换行格式差异不会被当作路由变更。两个参数可按本次需要组合；`-Server` 和 `-IdentityFile` 可指定服务器及登录密钥路径。

`-UpdateSecrets` 同步支付配置时将本地 `mock` 模式转换为服务器 `disabled`，避免预览中的模拟发放入口被一并开放；普通发布继续保留远端原有环境文件。真实付款必须单独明确启用，详见 [支付接入](PAYMENTS.md)。

## 发布流程与结果

脚本比较文件内容摘要（SHA-256，用于确认文件内容是否一致），仅上传新增或变化文件。远端在发布锁内确认上传准备期间的在线文件没有被另一轮发布修改，验证上传清单与文件摘要，先完成可校验的私有快照，再覆盖源码和配置。代码快照包含发布前的代码、配置、网站证书及本项目密钥；业务数据存入独立快照。

修改服务源码或运行配置时重建本项目容器，随后检查 Compose 配置、Nginx 配置、服务启动、本网站状态与既有支付路由。检查只使用读取请求，不生成订单、不发送支付回调。

快照位于 `.backups/<发布标识>/`，包括 `manifest.json` 文件清单、`manifest.sha256` 清单摘要和 `files/` 下的恢复文件。发布记录位于 `.releases/<发布标识>.json`，保存代码提交、执行结果和恢复信息。结束时记录脚本输出的发布标识并核对状态：

- `deployed` / `rolled_back`：发布 / 手动回退通过自动服务检查，还需完成本次功能的必要页面验证。
- `failed_preflight`：发布准备检查失败，尚未覆盖在线文件。
- `failed_rolled_back`：本次操作失败，已自动恢复到操作前的文件与服务；修复后重试。
- `failed_recovery`：自动恢复未通过检查；保留失败记录与快照，先按错误输出排查配置、网络及依赖，不连续覆盖发布。
- `failed_no_previous`：首次部署等场景缺少完整旧版，没有可恢复版本；保留记录并修复问题。

同一台服务器上的发布锁保护本工具发起的发布和回退；支付仓库的独立发布工具不受该锁管理。共享入口调整需避开另一个仓库的同时发布，在线文件变化检查不能代替跨项目协调。

## 手动回退

`ReleaseId` 是发布前快照的标识。选择某次发布的标识，将恢复到那次发布开始之前的文件状态，而不是恢复那次发布的新代码：

```powershell
.\deploy\Rollback.ps1 -ReleaseId <发布标识>
```

该入口只接受新流程生成、带文件清单及摘要的目录快照。此前手工创建的整目录压缩备份不能直接传给 `ReleaseId`，也不能直接覆盖在线目录；需要按本项目代码、数据和外部支付文件的边界另行制定恢复步骤。

脚本先校验目标快照完整性，并分别备份回退前的当前代码和业务数据，再恢复代码、配置、本项目密钥及网站证书，移除目标版本没有的新增源码，重新启动并检查服务。当前 `data/` 中的留言、限制记录和账号数据库始终保留。

若目标快照的共享 Nginx 配置与线上不同，默认停止回退，以免撤销支付项目后续的入口调整。核对差异、确认允许一起恢复共享入口后才加参数：

```powershell
.\deploy\Rollback.ps1 -ReleaseId <发布标识> -UpdateProxyRoutes
```

手动回退失败时尝试恢复回退前的文件状态，并保留恢复结果。因证书过期、外部依赖不可用等原因，文件恢复成功仍可能无法通过服务检查，应以最终检查和记录为准。

## 用户数据备份与恢复

应用层设有有界读取保护：支付查询每账号每分钟 60 次、每 IP 每分钟 120 次，同一订单的并发查询合并，订单操作最多每单排队 8 个、全局 256 个；会话读取每 IP 每分钟 120 次，临时浏览器标识不会在会话读取时写入账号关联表，单账号最多保存 100 个浏览器关联。AI 接口合计每 IP 每分钟 10 次，拒绝非规范请求路径；留言读取每 IP 每分钟 60 次，存储队列每文件最多 64 个、全局 512 个，已验证的数据按文件版本缓存。超限返回 429，正常付款通知仍直接验签和入账，不进入这些读取队列。读取限额在进程内统计，重启后重新开始；多实例部署时需要统一限流和存储协调。

发布和手动回退前，自动将本项目 `data/` 备份到 `.data-backups/<本次操作标识>/`，包含文件清单、清单摘要及 `files/` 下的数据文件，发布记录通过 `dataBackupId` 关联它。备份失败会停止本次操作。该目录与代码恢复快照分离，自动和手动代码恢复均不读取或恢复它。留言正文、签名密钥、限制记录及账号数据库都属于私有数据，备份目录需要纳入私有异地备份，保留策略由维护者管理。

账号 SQLite 数据库使用在线备份 API 生成一致性快照，包含已提交的 WAL 数据，并执行 `integrity_check`。Python 支持 SQLite 备份 API 时直接使用；生产环境 Python 3.6 由现有 app 容器中的 Node 24 完成在线备份。快照仅保存独立数据库文件，不复制运行中的 WAL/SHM 日志；任何备份或完整性检查失败都会阻止发布。其他数据文件仍按校验摘要复制，备份期间发生变化则停止并要求重试。不同数据文件之间不承诺跨文件事务一致性。

若确实发生数据丢失或损坏，应单独开展数据恢复：先保存现有数据和故障证据，确认备份完整性、恢复时间及影响范围，再停止本项目的数据写入，制定并执行恢复步骤，恢复后验证留言读取、当天限制及账号权益状态。数据恢复必须考虑备份后的新增留言、账号及权益记录，不能直接套用代码回退命令。不要发布测试留言到公开留言板。

恢复旧留言备份会丢失备份之后的新留言及当日限制记录，因此不能把数据恢复作为每次发布失败的默认动作。本项目订单和权益的数据恢复需与支付服务对账，防止已付款记录丢失或重复发放；商户侧支付数据问题由支付项目的恢复流程处理。

## 上线检查与维护

- 确认 `https://type.where.work/` 与 `/api/status` 可用，页面资源与本次版本对应；按变更范围检查导入历史、练习、翻译或表达评析。
- 确认 `/payments/` 仍跳转到支付演示页面，`https://pay.where.work/health` 和既有文档/演示入口可读取。检查支付回调转发配置即可，避免向回调发出测试写入。
- 确认 `/payments/notify` 精确路由转发到本项目应用而不跳转到演示页。发布健康检查保持只读；真实支付验收单独使用私有固定 1 分订单，经微信实际付款后核对签名通知、HTTP 200 ACK、订单与权益记录，不发送伪造通知代替真实验收。
- 核对服务器支付模式：公网不得开放模拟成功接口，真实付款仅在 `ZIJIAN_PAYMENT_MODE=live` 与 `ZIJIAN_ENABLE_REAL_PAYMENTS=1` 同时设置、私有配置完整时启用。API 签名密钥与业务通知密钥分开保管；轮换和故障排查见 [支付接入](PAYMENTS.md)。
- 付款通知异常时，可信维护者可使用 `payment-admin.mjs status --order ORDER` 读取本地快照，再针对已确认付款订单使用 `retry-notification --order ORDER` 重投原通知；工具没有公开管理接口，不创建新收款。实际数据库路径、运行模式及命令说明见 [私有订单排查](PAYMENTS.md#私有订单排查)。
- 真实验收使用 `payment-admin.mjs create-acceptance --user USER_ID --request STABLE_UUID --database AUTH_SQLITE_PATH`，只为既有账户创建固定 1 分 / 1 天内部订单，不接受改价，不加入公开套餐。核对应用审计记录 `payment_notification_ack` 的 `eventId`、`status: ACK` 与 `httpStatus: 200`，再验证重复通知不会重复发放；日志不记录通知签名、正文或凭据。2026-10-17 的真实付款与通知重投验收已通过，脱敏结果见 [验收记录](PAYMENTS.md#验收与当前范围)。
- `http://type.where.work` 应返回 308 跳转到 HTTPS 并保留路径和参数；IP 地址不在网站证书覆盖范围内。服务器安全组需允许 TCP 80、443。
- 域名、协议或端口变化时，同步调整 Compose 的允许网站地址及 Nginx 入口。当前 `ZIJIAN_TRUST_PROXY=1` 只适用于受信任入口覆盖真实访客地址的部署方式。
- 本项目的证书续期目前需替换本机证书及私钥后重新部署，没有自动续期任务。支付域名的证书续期由支付项目负责。
- 入口对翻译、学习分析、表达评析及标题请求共用限速，服务端另限制最多 3 个上游并发；公开站点使用服务器所配置账户的模型额度。
- 定期检查服务器磁盘、备份可读性、证书有效期及发布记录。私有快照包含密钥，按私有备份管理；异地备份和保留周期尚未自动化，应按需要另行安排，不能将同盘快照视为整机故障备份。
